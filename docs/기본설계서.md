# 기본설계서

## 1. 목적과 범위

방범대의 에피소드 기록을 브라우저에서 열람하고 관리하는 웹 애플리케이션이다. 에피소드의 운영 원본은 MongoDB이며 프런트엔드는 API를 통해 읽고 쓴다. 관리자는 변경을 직접 반영하고, 일반 사용자는 관리자가 승인할 변경 요청을 제출한다. 기존 `data/episodes.json`은 원본 보존·최초 적재·수동 백업 교환 파일로 남긴다.

## 2. 사용자와 권한

| 사용자 | 열람 | 직접 변경 | 변경 요청 검토 | 계정 관리 |
|---|---|---|---|---|
| 비로그인 사용자 | 로그인 화면만 이용 | 불가 | 불가 | 불가 |
| 일반 사용자 | 로그인 후 메인 사이트·편집기 이용 | 불가 | 본인 요청 제출 가능 | 불가 |
| 관리자 | 로그인 후 전체 기능 이용 | 즉시 추가·수정·삭제·순서 변경 | 승인·거절 가능 | 일반 계정 생성·활성화·비활성화 |

서버에서도 역할을 검사한다. 브라우저에서 버튼을 숨기는 것만으로 권한을 보장하지 않는다. 메인 페이지 로그인은 화면 접근 정책이며, 공개 조회·내보내기 API는 별도로 인증 없이 제공된다.

## 3. 주요 기능

### 메인 사이트

- DB의 전체 에피소드를 표시 순서대로 조회한다.
- 에피소드 본문, 인물 검색, 시기별 목차, 별자리 시각화를 제공한다.
- 기본 이름·시작 연도·시기 설정은 `data/squad.json`에서 읽는다. 에피소드에 포함된 새로운 시기도 목차에 추가한다.
- 로그인하지 않은 사용자는 `login.html`로 이동한다.

### 에피소드 편집기

- DB 에피소드 목록을 검색·시기 필터링하고 한 항목씩 편집한다.
- 관리자는 변경을 DB에 즉시 저장한다.
- 일반 사용자는 추가·수정·삭제·순서 변경 요청을 제출하며, 승인 전에는 공개 DB 데이터에 반영되지 않는다.
- 전체 내보내기는 검색 결과가 아닌 DB 전체를 표시 순서대로 JSON으로 다운로드한다.

### 관리자 승인 및 계정 관리

- 승인 대기 요청을 목록에서 선택하고 원문과 제안 내용을 좌우 비교한다. 변경 문자열은 수정 제안 쪽에서 강조한다.
- 동일 요청 항목을 다시 누르면 상세를 닫는다.
- 관리자는 요청을 승인하거나 거절하고, 일반 사용자 계정을 발급·활성화·비활성화한다.
- 대기 목록은 15초 간격으로 갱신된다.

## 4. 데이터 원칙

- 에피소드의 운영 원본은 MongoDB `episodes` 컬렉션이다.
- `data/episodes.json`은 삭제하거나 운영 시 자동 덮어쓰지 않는다. DB 최초 적재 입력이며, 다운로드한 백업을 별도로 보관하는 데 사용할 수 있다.
- JSON 파일과 DB는 자동 동기화되지 않는다. 운영 DB 백업은 편집기 전체 내보내기를 이용하고, DB를 파일 내용으로 재적재할 때는 백업·대상 확인 후 절차를 수행한다.
- 에피소드 배열 순서는 사이트 표시 순서다. DB 내부에서는 `order`로 관리하고, API 결과는 순서가 반영된 배열로 응답한다. JSON 내보내기에는 DB 식별자와 `order`를 포함하지 않는다.
- `bright: true`는 사이트에서 제목에 레전드 표시를 붙이는 선택 필드다. 기본값은 false이며 내보내기에는 true일 때만 포함한다.

## 5. 시스템 구성과 기술

| 영역 | 구성 |
|---|---|
| 프런트엔드 | HTML, CSS, ES modules |
| API 서버 | Node.js 20+, Express 5 |
| 데이터베이스 | MongoDB Node.js driver |
| 보안 관련 구성 | Helmet, scrypt 비밀번호 해시, HMAC 서명 세션 토큰, 역할 검사, 로그인 시도 제한 |
| 설정 | 브라우저 API 주소는 `js/api-config.js`; 서버 비밀·DB·CORS 설정은 `backend/.env` |
| 테스트 | Node.js 내장 `node:test`, 루트 명령 `npm test` |

승인 적용, 에피소드 삭제, 순서 변경은 MongoDB transaction을 사용한다. 따라서 서버는 replica set 또는 호환되는 MongoDB Atlas 환경이 필요하다.

## 6. 실행과 배포

### 로컬 개발

1. MongoDB replica set을 실행하거나 Atlas 연결 정보를 준비한다.
2. `backend/.env.example`을 참고해 `backend/.env`를 작성한다. `.env`는 저장소에 커밋하지 않는다.
3. 백엔드 의존성을 설치한다: `npm --prefix backend install`.
4. 기존 에피소드를 DB에 최초 적재한다: `npm run import:episodes`. 대상 `episodes` 컬렉션이 비어 있지 않으면 스크립트는 적재를 중단한다.
5. API를 시작한다: `npm start` (기본 포트 3000).
6. `js/api-config.js`의 API 주소를 로컬 주소로 두고 프런트엔드를 Live Server 등 HTTP 서버로 연다. `file://` 실행은 지원하지 않는다.
7. `npm test`로 테스트를 실행한다.

### 배포 전 확인

- `js/api-config.js`를 운영 API origin으로 지정한다.
- 백엔드 `FRONTEND_ORIGINS`에 프런트엔드 origin을 정확히 등록한다.
- HTTPS, 강한 `SESSION_SECRET`, 운영 DB 연결 문자열 및 관리자 계정 환경 변수를 구성한다.
- MongoDB replica set이 활성화됐는지 확인한다.
- 기존 `data/episodes.json`과 DB 백업을 구분해 보관한다.

## 7. 현재 범위와 제약

- 메인 사이트와 편집기는 서비스 실행 중 API와 DB에 연결할 수 있어야 한다.
- 공개 배포 환경의 API·DB 연결 및 실브라우저 end-to-end 동작 여부는 환경별로 별도 확인해야 한다.
- `data/squad.json`은 현재 정적 설정으로 유지되며 DB 설정 컬렉션으로 이전하지 않았다.
- 이메일·푸시 알림은 없으며 관리자 화면의 주기적 조회로 승인 요청을 확인한다.
- 브라우저 토큰은 `sessionStorage`에 저장된다. 서버에서 별도 세션 폐기 목록을 관리하지 않으며 토큰은 발급 후 12시간까지 유효하다.
- API 상세, 데이터 검증, 충돌 처리 내용은 [상세설계서](상세설계서.md) 및 [편집기 사양](editor-spec.md)을 참조한다.
